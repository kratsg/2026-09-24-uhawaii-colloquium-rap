Hi, I'm Giordon, I build analysis-facility infrastructure at UChicago for ATLAS. Three slides, big picture. The way I think about an agent is three blocks. The model, which you can swap: frontier API or open weights you host yourself. The harness, Claude Code, Codex, Copilot, also swappable. And the third block, the facility's context and tools: where the data lives, how you submit jobs, who you are. That third block is the only durable, tractable piece, and it's the one we control. This is the "just furnish context" point from the paper on the agenda, but in practice furnishing context is an infrastructure problem, not a prompt problem. Flip side: context isn't only what makes an agent useful, it's what makes it safe to trust. Our cluster agents confidently recommended Lustre tuning on a filesystem that's actually Ceph. So our rule is ungrounded means silent.

This is the platform in one animated call: the portal landing page's own diagram, reproduced in the slide. Let it run one cycle while talking. Two authorized calls play through: the assistant asks, Auth, Policy, and Audit check green, the Broker mints a credential off to the side, the call lands on Rucio or HTCondor, and the answer comes back. The third cycle is the governance story in eight seconds: "Delete my /data datasets" passes Auth, fails Policy, the gateway buzzes red, and the assistant reports it is not authorized. Three things to say over it: credentials stay behind the broker, so the assistant never holds anything raw and the user's token is never forwarded downstream. Every call is authorized against group-based permissions, and the denials get audited too. And every credential is minted short-lived for exactly one service, used once, and deleted. And the design idea underneath, which I showed at Nikhef: the agent speaks intent, "get this dataset", "run this on the cluster", and the facility wires that to Rucio, HTCondor, whatever the backend is. Adding the next MCP server is configuration, never a change to the server.

Secure the architecture, design the interface

Security is structural

  • No tool takes a username: identity comes from the verified token, never the LLM
  • No credentials in the MCP: vault → mint per call → use once → delete
  • Permissions decided once, at the gateway; new tools are opt-in

Agents are only as good as their tools

  • One domain per server, with written non-goals
  • Docstrings are the manual: tested against the live service
  • Bounded outputs; errors name the next tool to call
Interoperable tool interfaces are likely to matter more than model-specific integrations.

Security, saved for the end as requested. The key idea: don't ask the model to be trustworthy, make the architecture not care. No tool in our fleet takes a username, so the schema literally can't express "read Bob's files"; who you are comes from the verified identity on every call. No MCP server holds a credential: the broker pulls from a vault, mints something short-lived for exactly one service, it's used once and deleted. And permissions are decided in exactly one place, the gateway, from plain group-based RBAC. A brand new tool stays off until an operator maps it. The other half is agent design. The model experiences your tools only through names, docstrings, outputs and errors. So: one domain per server. Docstrings are the model's manual; ours reproduced a broken example verbatim, so now they're tested against the live service. Bound every output, since raw API rows swamped the model. And errors should say what to call next so the agent recovers. Close: interoperable tool interfaces will matter more than model-specific integrations. Design the interface for the model, design the architecture for the credential.
